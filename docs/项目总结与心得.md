# 智能干湿提醒衣架 — 工作总结与心得

> 项目周期：2026-11-08 ~ 2026-11-10
> 仓库分支：`feat/dry-wet-rack`

---

## 一、项目背景

这个项目起源于一个已经跑通的「环境监测仪」：ESP32-S3 + AHT30 温湿度 + SGP30 气体传感器 + ST7789 屏，能在屏幕上显示温度、湿度、CO₂ 和 TVOC。

转折点出现在硬件层面——SGP30 在多次更换、多块板子上都无法在 I²C 地址 0x58 应答，最终确认是模块故障。把传感器拆掉之后，剩下的 CO₂ / TVOC 逻辑全成了死代码，而"监测空气"这个场景本身也偏弱：看一个数字，然后呢？

重新找定位时，想到一个更实际的问题：**晾衣服时，我到底还要晾多久？**

于是项目从"环境监测"转向"干湿提醒"：

- 用温湿度判断衣物所处的干燥程度
- 联网把结果推到手机上
- 支持低功耗，挂在那儿三十天才想起来看一眼也不至于没电
- 更进一步，直接算一算"还有多久能干"

---

## 二、主要工作

### 1. 硬件梳理与软件裁剪

第一步不是写代码，是**把硬件搞清楚**。

从原理图逐脚核对后发现两件之前文档里没写的事：

| 发现 | 影响 |
|------|------|
| TFT 的 `BLK` 引脚悬空（打叉） | 背光直接吃 VCC，软件关不掉 |
| `IO2` 接了电池电压分压（R3/R4 各 100 K） | 不能用作其他用途，也解释了为什么不能用 Freenove 板型 |

同时确认了 BOOT 键的电路：`IO0` 经 10 K 上拉到 3V3、并 100 nF 消抖。这直接决定了低功耗的唤醒方案可行。

软件上把 SGP30 整条链路拆掉：
- 删掉 `sgp30_driver` 组件
- I²C 从双总线简化为单总线
- 清掉 NVS 基线存储、CO₂ 阈值、仪表盘的 CO₂/TVOC 区域

> 删代码比加代码难。SGP30 虽然只是"一个传感器"，但它散落在 `app_core`、`app_config`、`nvs_storage`、`ws2812`、`app_display` 五处，删的时候必须顺着引用一路捋。

### 2. 显示系统重做

原界面是"CO₂ 大数字 + 温湿度"，新界面围绕"干湿状态"重新设计：

```
干湿提醒                    配网中
温度        湿度
25.2°C      36%
████░░░░░░       干燥
预计 5.0 小时
露点 9.2°C
绝对湿度 8.5 g/m3
```

技术路径沿用原项目的"预渲染 4bpp 位图 + alpha 混合"方案，用 `generate_display_assets.py` 重新生成全部素材（新增"干燥/适宜/偏潮/潮湿"状态字、"预计/小时/分钟"等单位）。

### 3. 联网与主动通知

按"设备主动推，而不是等我去看"的思路设计：

**配网**：首次开机检测 NVS 无凭据 → 开热点 `DryRack-XXXX`，手机连上后浏览器打开 `192.168.4.1` 填表，保存进 NVS 后重启连路由器。换路由器时长按 BOOT 8 秒清配置。

**上报**：支持四种 webhook 格式，覆盖常见场景：

| 格式 | 用途 |
|------|------|
| 通用 JSON | 自建服务 |
| text | 企业微信 / 钉钉机器人 |
| 飞书 | 飞书自定义机器人 |
| Bark | iOS 推送 |

**本地服务**：设备还跑一个 HTTP 服务，局域网内可直接看实时数据、远程下发休眠指令。

### 4. 低功耗

设计约束是硬件给的：ESP32-S3 只有 **GPIO0~GPIO21** 属于 RTC IO 能作为深睡唤醒源，而板上的开关机键在 IO39，**根本叫不醒芯片**。

所以分工是：

- **IO39 长按 2 秒** → 进入深睡
- **BOOT (IO0) 按一下** → 唤醒
- **RTC 定时器 30 分钟** → 静默唤醒一次，采数据、连 WiFi、推一条消息、继续睡

定时唤醒路径**完全不初始化屏幕**，尽可能缩短唤醒时间。

### 5. 预计干衣时间

这是整个项目里唯一"有算法含量"的部分。

物理出发点是：衣物水分蒸发速率正比于剩余含水量，所以在环境稳定时，晾晒过程中的相对湿度按指数衰减：

```
RH(t) = RH_floor + A · e^(-k·t)
```

**实现分两条路**：

1. **趋势外推**（有历史时优先）
   每 60 秒记一个点，保留 96 个（约 1.6 小时）。当样本 ≥ 10 且湿度确实在下降时，对 `ln(RH − RH_floor)` 做最小二乘拟合求衰减常数 k，再外推到目标湿度。

2. **VPD 物理兜底**（刚上电 / 低功耗刚唤醒）
   `VPD = es(T)·(1 − RH/100)`，干燥时间近似反比于 VPD。经验常数按「25°C / 50%RH ≈ 6.5 小时」标定。

另外做了**自动识别挂衣**：湿度 1 分钟内突升超过 6 %RH，判定为刚挂上湿衣服，历史曲线自动清空重记。

### 6. 工程化

- 所有改动在新分支 `feat/dry-wet-rack` 上进行，`master` 保持原样
- README 写了功能、配网、webhook 格式、低功耗行为、硬件约束
- `esp.md` 记录架构与决策
- 原理图、PCB、器件照片归档到 `docs/hardware/`
- 演示视频剪成 56 秒，关键画面作为截图放进 `docs/screenshots/`

## 三、踩过的坑

这部分比"做了什么"更值得记。

### 坑 1：外部组件在 IDF v6.1 下编译不过

`espressif/led_strip` v2.5.5 的 SPI 后端用了 `heap_caps_calloc` 却没 `#include "esp_heap_caps.h"`，IDF v6 不再间接包含这个头文件，直接编译失败。

**解决**：不再修它，改用**原生 RMT 重写 WS2812 驱动**（约 130 行）。20 MHz 分辨率下把每个 bit 编码成一个 `rmt_symbol_word_t`（bit0 = 8/17 tick，bit1 = 16/9 tick），彻底去掉外部依赖。

**体会**：遇到第三方组件不兼容，评估"修它"和"自己写"的成本。这次自己写反而更快，也更可控。

### 坑 2：IDF 5 → 6 的 API 迁移

| 旧 | 新 |
|---|---|
| `esp_lcd_panel_dev_config_t.color_space` | `rgb_ele_order`（v5.2 起） |
| `esp_sleep_get_wakeup_cause()` 返回枚举 | `esp_sleep_get_wakeup_causes()` 返回 `BIT(cause)` 位图 |
| `driver` 组件包含所有驱动 | 拆成 `esp_driver_i2c` / `esp_driver_spi` / `esp_driver_rmt`… |

**体会**：跨大版本迁移前先读 changelog，比逐个编译报错试出来省时间。

### 坑 3：屏幕上的数字叠字

用户发来照片，屏幕上 `25.9` 里叠着一个 `8`。两个 bug 撞在一起：

1. **擦除区域没盖住数字**——重绘从 `y=122` 开始，但温度/湿度数字画在 `y=72`，压根没被擦，新数字直接盖在旧数字上
2. **小数点飘到顶端**——`draw_string` 把所有字符顶部对齐，而小数点素材只有 6 px 高，就贴到数字顶上去了

**解决**：擦除起点改为 `y=42`（标题栏下方），小数点按基线对齐、负号垂直居中。

**体会**：帧缓冲直驱的方案性能好，但每个像素都要自己管。这类 bug 只有**真机照片**能看出来，仿真和看代码都发现不了。

### 坑 4：网页下发休眠会把设备卡死

最初在 HTTP handler 里直接调用休眠函数，结果 `httpd_stop()` 要等当前 handler 返回，而 handler 又在等 `httpd_stop()`——死锁。

**解决**：handler 只置一个标志，由上报任务真正执行休眠。

### 坑 5：关屏后又被采集任务刷亮

`sensor` 任务每秒写帧缓冲并 `flush()`，进低功耗关屏后它立刻把屏幕刷回来。

**解决**：新增 `app_core_suspend_updates()`，休眠前先冻结刷新，并给足 300 ms 让当前一轮采集结束。

### 坑 6：烧录失败五六次，全是硬件的锅

这段最有教育意义：

| 现象 | 真实原因 |
|---|---|
| `No serial data received` | **电池欠压**（烧录瞬间电流大，电压跌落） |
| 烧录成功但串口完全静默 | **BOOT 键还按着**，芯片复位后直接进下载模式 |
| 复位后仍无输出 | esptool 退出后 `RTS` 把 `EN` 留在复位态，要手动按一下 EN |

从 ROM 日志里能清楚看到证据：

```
rst:0x1 (POWERON),boot:0x31 (DOWNLOAD(USB/UART0))     ← BOOT 按着，进下载模式
waiting for download
rst:0x1 (POWERON),boot:0x39 (SPI_FAST_FLASH_BOOT)     ← 松开 BOOT 复位，正常启动
```

**体会**：一开始总怀疑代码或工具链，实际上 **90% 的异常是硬件状态**。以后先看三样：有没有电、复位键什么状态、按键是不是还按着。

### 坑 7：PowerShell 把源码编码改坏了

用 `(Get-Content -Raw) -replace ... | Set-Content -Encoding utf8` 批量替换文本，结果 `Get-Content` 按 GBK 读 UTF-8 文件，中文全变乱码，再写回去就成了双重编码。

**解决**：`git checkout` 恢复，改用编辑器工具重做。

**体会**：**不要用 shell 文本替换改源码**，尤其是有中文的源文件。工具链的隐式编码转换非常危险。

### 坑 8：飞书机器人收不到消息

配好 webhook 后收不到，返回：

```json
{"code":19024,"msg":"Key Words Not Found"}
```

原因是加了「自定义关键词」校验，而关键词不是消息里的词。

**解决**：关键词改成 `干湿衣架`（固件消息固定以「【干湿衣架 XXXXXX】」开头）。

**教训**：对接第三方服务时，先用 curl / PowerShell **单独测通**，再往设备里填。这次提前测出来了，否则会在设备上反复烧录排查。

## 四、心得

### 1. 先硬件，后软件

这次最深的体会。烧录、联网、显示的问题，绝大多数根因在硬件层：电量、复位电路、引脚、按键状态。代码写得再对，硬件状态不对也是白搭。

养成习惯：出问题先问"硬件现在是什么状态"，再去看代码。

### 2. 依赖越少越稳

去掉 `lvgl` 和 `led_strip` 两个外部依赖后，工程变成"首次编译无需联网下载"。自己写的 WS2812 驱动 130 行，比调试上游组件的兼容性问题更快。

不是说要造轮子，而是**评估依赖时要把"未来迁移成本"算进去**。

### 3. 能解释的算法才敢用

干衣时间如果只写个"经验公式"，别人问"为什么"就答不上来。从"蒸发速率正比于剩余含水量"推出指数衰减，再用最小二乘拟合——这个推导过程让参数有了物理意义，也让"没有历史数据时怎么办"的兜底方案自然浮现。

### 4. 低功耗是系统问题，不是一句 sleep

一开始以为调用 `esp_deep_sleep_start()` 就完事了，实际要处理：

- 屏幕要不要关（`DISPOFF` + 背光）
- 采集任务会不会把它刷亮
- WiFi 怎么优雅关闭
- 唤醒源配失败了怎么办（必须有兜底，否则变砖）
- 背光硬件上根本关不掉怎么办

最后一条是硬伤：**BLK 悬空意味着低功耗收益打折**。这属于设计阶段该考虑的事，软件补不了。

### 5. 删比加难

拆掉 SGP30 只花了半小时写代码，但捋清楚它在五处文件里的引用花了一倍时间。**功能模块的"散落度"决定了删除成本**，以后设计时尽量让模块自包含。

### 6. 文档即生产力

把原理图逐脚核对、写成引脚表，后面调试时直接对照，省了很多"这个脚接哪来着"的反复。同理，把踩过的坑记进 `esp.md`，下次遇到类似问题能秒查。

### 7. 不确定就问，别猜

板型、webhook 格式、低功耗行为，这些都涉及"用户到底想要什么"。问清楚了再写，比写完返工省事得多。这次一开始就问了三个关键问题（通知方式、配网方式、低功耗行为），后面没出现大的返工。

## 五、不足与改进方向

诚实列一下没做好的地方：

| 问题 | 说明 |
|------|------|
| 电池电压检测未实现 | 原理图预留了 IO2 分压，但固件没读，无法显示电量 |
| 背光不可控 | BLK 悬空，低功耗时仍耗电十几 mA，需飞线改硬件 |
| 无 RTC | 深睡后时间戳依赖 `uptime`，通知时间以接收端为准 |
| VPD 常数未校准 | 103 是按经验值定的，没有针对不同衣物厚度做标定 |
| 单传感器无冗余 | AHT30 异常时没有交叉校验手段 |
| 无 OTA | 升级固件仍需插线烧录 |
| 演示视频未入仓 | 43 MB 不适合放 Git，应走 Release 附件或外链 |

如果继续迭代，优先级会是：**飞线接背光 → 实现电量检测 → OTA → VPD 参数自校准**。

---

## 六、总结

这个项目从"删掉一个坏掉的传感器"开始，最后变成一套完整的产品化功能：干湿分级显示、无感配网、主动推送、低功耗周期采集、以及一个能解释的干衣时间预测。

技术上的收获是具体的：ESP-IDF v6 的迁移、RMT 手写驱动、帧缓冲像素级调试、指数拟合与物理模型结合。

但更重要的可能是方法上的：**先搞清硬件、先测通外部服务、不要用 shell 改源码、出问题先怀疑物理环境**。这几条比任何一行代码都更通用。
